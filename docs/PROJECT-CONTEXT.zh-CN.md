## 1. 起点：便捷的 Windows 实时翻译，而不是固定方向的字幕演示

**用户已确认的直接指令摘要：** 新建项目文件夹，读取本地 GitHub CLI 配置并建立开源项目；在电脑后台运行，只显示不影响日常操作的小弹窗，捕获电脑音频输出并翻译；先用高效模型保障实时性，再试本地大模型或 API 做即时/后期修正；初版不做自动语言检测。随后明确纠正语言范围：不得固定英语到中文，至少覆盖中、日、英、韩互译。

由此保留的产品意图是“先有可用字幕，再按需精修”，不是强制所有内容等待大模型。四语需求是 12 个有向语言组合，不能因某次 EN→ZH 测试较完整就缩减产品方向。模型支持更多语言也不自动等于产品已经承诺其质量。

仓库依据：[ADR 0001：快译与修正分离](decisions/0001-fast-path-and-revision-path.md)、[ADR 0002：四语手动选择](decisions/0002-four-manual-languages.md)、[架构](ARCHITECTURE.md)。这些 ADR 记录了当时接受的技术方案，不要求永远使用某个厂商或模型。

## 2. M0–M5：先贯通可用链路，再形成首个发行版

用户在相邻任务中逐次确认推进到 M1、M2、M3、M4、M5；M3 追加仅译文/双语显示与 EXE、安装包准备，M5 明确要求正式打包并发布首个版本。以下里程碑划分与实现归属来自[路线图](ROADMAP.zh-CN.md)和[变更记录](../CHANGELOG.md)，不为没有日期的用户消息补造时间。

| 阶段 | 当时目标与已确认推进范围 | 后续不能误读为 |
|---|---|---|
| M0 | 建立仓库、许可、配置、基础 UI、架构和模型许可记录 | 用户要求了账号、云同步或跨平台产品 |
| M1 | 系统音频捕获、归一化、设备选择与稳定性检查 | 所有设备、所有未来捕获路径均已验证 |
| M2 | 四语显式语言识别、增量结果与模型基准 | Whisper 已变成严格逐 token 流式模型，或所有硬件都满足低延迟 |
| M3 | 12 方向快译、仅译文/双语悬浮窗、历史，并准备 EXE/安装包 | 后续任务一律需要重建安装包 |
| M4 | 可选本地或 API 大模型修正、修订记录和失败回退 | 云端默认开启，或 LLM 必然提升每条字幕质量 |
| M5 | 质量/打包门禁与首个公开 Windows 版本 | 历史 `all_passed` 等于长期、全语言、真实设备体验全面达标 |

本地变更记录将首发记为 v0.1.0。首发中的量化结果应按[基准索引](benchmarks/README.md)所列的原日期、硬件、模型和样本解释，不能移用为当前提交的性能证书。

## 3. 0.1.x：从可运行到易用，解决字幕堆积与误署名

**用户已确认的直接指令摘要：** 增加悬浮窗拖动和缩放、安装时检查已有模型；长语音不要一次堆出大量文字；模型加载完成应明确提醒，尽快显示识别并实时翻译，遇到明确断句应切段；改善历史窗口，使用更简洁的图标；增加字幕保留时间、字体颜色等统一设置页面；项目制作人和版权所有者改为 **Leeleelee**；增加软件与模型卸载能力。

署名要求指项目元信息与版权归属，不是把所有媒体中的制作人识别文本都替换为 Leeleelee。用户指出的“字幕制作人 Zither Harp”属于需要检查的异常识别现象；仓库随后采用可关闭的短署名模板过滤。过滤实现不能代替真实语音质量验证，也不能被扩大为任意删除正常媒体文本的授权。

这些诉求对应 CHANGELOG 中 v0.1.1、v0.1.2 等记录；较早的十秒字幕上限后来被 0.1.5 的默认六秒及可选配置演进，不应把历史默认值覆盖回当前设置。

**签名决策：** 用户询问如何签名后明确暂不考虑签名。因此保持“尚未签名”的诚实提示，不能自行购买证书、签署身份或把自签名包装成受信发行；这也不是永久禁止未来讨论签名。卸载与模型卸载不等于授权清空配置、历史、录音、导出文件或用户自行放入的模型。

仓库依据：[变更记录](../CHANGELOG.md)、[隐私说明](PRIVACY.zh-CN.md)、[发布流程](RELEASE.md)、[第三方许可](../THIRD_PARTY.md)。

## 4. 技术参考与 0.1.5 综合优化

**用户已确认的直接指令摘要：** 讨论如何优化识别质量、实时性、稳定性和性能占用；询问 YouTube 和其描述的“Outlook 会议”实时字幕/翻译是否可作技术参考；随后要求设计第一版优化，整合 LLM 设置、精简弹窗上的常用按钮、改进安装文本与模型选择指引，并推进到 v0.1.5；之后要求参考优质开源项目改进 GitHub 项目页面与 README。

产品参考的含义是研究交互和工程方法，不是确认接入 YouTube/Outlook/Teams 的服务、私有接口或用户账号，也不是要求读取邮件、会议或私人录音。不能声称已复现这些商业系统的内部实现或质量水平。

仓库将该轮方案记录为[0.1.5 优化设计](OPTIMIZATION-v0.1.5.zh-CN.md)：包括字幕配置档、增量推理频率调整、上下文提示、现有标点端点、可选 LLM 和模型安装引导。其设计目标不是无条件性能承诺。界面始终保留“简洁、少打扰”的初衷，不因新增功能把悬浮窗变成完整控制面板。

## 6. 0.3：录制、媒体导入与时间轴后期工作台

**用户已确认的直接指令摘要：** 可以任意时间开始、暂停、结束录制，对录制音频做更准确的后期识别与翻译；录制同样可选择整个电脑、某个进程或某个麦克风；文本应与音频时间轴对齐，支持多格式输出；另外支持音频导入和视频音轨分离后处理。用户先要求方案与未来更多语种建议，随后明确开始开发并完成 v0.3.0。

原始需求中出现 `mp3.vtt` 表述。当前实现将 MP3 音频与 WebVTT 字幕分别导出，可配对使用，并提供其他音频/字幕/数据格式；不要将其写成一种已经实现的单文件复合标准。若未来需要自动配对打包、双语排版或特定播放器格式，应重新确认输出交互。

此阶段明确改变了最初“实时音频仅在内存中”的范围：用户主动录制或导入时，项目允许将工作音频、项目元数据和字幕保存在本地。它不授权覆盖或删除导入的原始媒体，也不默认上传这些内容。录音片段恢复不等于后期推理断点续跑；只有高质量选项可选，也不等于每次自动处理都已经采用最佳模型或启用 LLM。

仓库依据：[v0.3.0 历史说明](releases/v0.3.0.md)、[隐私说明](PRIVACY.zh-CN.md)、[离线需求状态](REQUIREMENTS.zh-CN.md#录制与后期工作台)。更多语言是用户明确提出的未来方向，但首批语言、方向级质量门槛和具体发行范围仍需确认；候选方案见[扩语种设计](LANGUAGE-EXPANSION.zh-CN.md)。

## 7. Qt 启动故障与 0.3.3 开发快照

**用户已确认的直接指令摘要：** 新版本运行时在导入 `PySide6.QtCore` 阶段出现 DLL 加载失败，要求处理；随后要求检查仓库、优化代码与安装包，并使用本地配置的 OpenRouter 测试修正实时性和准确性。

仓库记录 v0.3.1 处理混入不兼容 ICU 导致的冻结 Qt 启动失败，v0.3.2 追加升级时精确清理旧冲突 DLL。这个教训是“开发环境可运行”不能代替最终 EXE 与升级路径验证，而不是以后遇到 DLL 问题就任意删除运行库或用户目录。

后续 0.3.3 开发快照包含 LLM 可靠性、连接复用、OpenRouter 设置、隔离发行环境、准确 SBOM、受依赖检查约束的包体裁剪和卸载保留用户文件。详细实施与证据仍以[变更记录](../CHANGELOG.md)、[历史本地验证](benchmarks/v0.3.3-local-validation.json)为准，不因存在本地安装器就标记已公开发布。

### OpenRouter 历史试验的边界

2026-09-07 日期、**当次授权预算 $1**、204 次调用及服务端报告费用 $0.00635959 均来自[已提交的试验报告](benchmarks/OPENROUTER-v0.3.3.zh-CN.md)，不是为无日期聊天补写的原话。核心质量样本是英语→中文，另有其他方向烟雾检查；使用的是项目自编文本，不是用户录音。不能把 EN→ZH 小样本模型辅助评审当成人工认证、四语全部质量认证或音频到屏幕的端到端延迟。

这次预算和模型选择只适用于该次试验。剩余额度不是后续轮次可重复支取的长期预算；本地存在 API 密钥也不是新增付费调用或上传私有内容的许可。新的真实 API 测试仍需确认提供商/模型、样本范围、预算和输出位置，不自动更改用户已保存配置或启用云端处理。

### 已发现的问题不能只留在聊天里

最近只读评估提出的重点包括：满 final 队列的等待/背压风险、质量门禁过宽、缺真实音频到屏幕与真实设备长会话证据、硬件/四语人工质量矩阵不足，以及长文件资源与取消边界。它们应在[已知问题](KNOWN-ISSUES.zh-CN.md)中保留证据、影响、优先级和关闭条件；本页不宣称这些问题已被修复。

特别保留两个容易误读的区别：

- 容量有界不等于等待时间有界；“保留 final”不是任意阻塞捕获或界面的理由。
- 录音合并按块读取只限制拼接阶段的额外内存，不证明整段 ASR 内存有界；逻辑测试、历史宽松门禁和小样本 API 成功率都不能直接证明强实时与高质量。

独立模型进程、真正流式 ASR、长文件推理分块/断点恢复、更多语言、项目批量管理、自动硬件调优等仍是需取舍的候选方案，不能因为出现在评估或路线图里就视作全部已获实现授权。下一项实际工作以[当前交接](HANDOFF.zh-CN.md)和用户当次确认的范围为准。

## 9. 每次继续工作时保留的授权与数据边界

1. **历史发布请求仅针对当次任务。** 用户曾多次要求开发完成后发布，并不授权后续自动增加版本、创建标签、上传发行物或启动安装器；最近维护明确“不发新版”的边界也必须保留。推送源码、生成本地产物、发布 Release 是不同操作。
2. **模型和网络操作显式。** 本地优先、LLM 可选；模型下载、付费 API、登录/外部系统操作遵守当次范围，不能从配置或密钥存在推断授权。
3. **原始媒体与用户数据受保护。** 不将私人录音、字幕历史、配置密钥、模型权重提交到仓库；导入只读原媒体，默认卸载保留用户数据，不把目录清理扩展成删除用户自建文件。
4. **先区分证据类型。** 功能存在、测试通过、某设备实测、人工质量评审和公开发布必须分别举证。无日期的聊天意图不伪造时间；有日期的旧报告不冒充新结果。
5. **新决定及时落盘，旧决定不悄悄消失。** 更新需求状态、必要的 ADR、已知问题与交接；不要靠增长的聊天历史记住尚未关闭的风险。若来源不足，明确写待确认，不填成既成事实。
